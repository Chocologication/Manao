## 1. 项目背景 & 目标

### 1.1 项目背景（三大痛点）

- 痛点一：环境配置门槛高
  - 初学者本地配环境、装依赖、配中间件、加环境变量繁琐
  - 被墙拉不下包、找不到安装位置、忘记配置依赖
  - 莫名其妙的报错严重打击学习兴趣
- 痛点二：临时演示场景受限
  - 忘带笔记本 / 本机未装 IDE 时无法临时演示
  - 网上在线编辑器质量参差不齐
- 痛点三：教学与竞赛环境难以统一
  - 不同终端 / 依赖 / 系统条件导致结果不一致
  - 教学演示难复现
  - 竞赛环境难统一
  - 运维支持成本高

### 1.2 项目意义与目标

- 核心意义：把"学代码、配环境、查资料、跑程序、看报错"整合为统一、可执行、可反馈、可追踪的在线开发闭环
- 用户在浏览器中即可完成
  - 创建项目
  - 编写代码
  - 获取 AI 辅助建议
  - 一键分配运行环境
  - 查看日志与运行结果
  - 根据 AI 分析继续修改优化
- 升级转变
  - 内容学习 → 智能实践
  - 静态平台 → 动态实验室
- 面向初学者的价值
  - 聚焦语法理解
  - 编程思维训练
  - 调试能力培养
  - 项目实战练习
  - AI 即时反馈：解释 / 分析 / 修改 / 优化 / 补全
- 面向教师与竞赛的价值
  - 统一教学环境，降低教学组织成本
  - 适合开展实践型竞赛项目
  - 综合展示前端 / 后端 / 云端 / AI / 监控五维能力

### 1.3 产品定位思路

- 目标用户：初学者 / 教师 / 竞赛团队 / 开发实践
- 应用场景：高校竞赛、程序设计实验、课程实践、开发者训练营、企业内部演练、初学者起步
- 核心闭环：用户提需求 → 平台分配容器 → AI 生成 / 建议 → 云端执行 → 返回日志结果 → AI 二次解释调优
- 定位差异：不是普通 AI Web，而是真正能"执行"的 AI 工具平台

## 3. 系统设计、技术选型与技术路线

### 3.1 整体架构思路（三层架构）

- 第一层 前端交互层：代码编辑、AI 对话、运行控制、结果展示、资源可视化、用户操作入口
- 第二层 后端业务层：用户认证、项目管理、团队管理、AI 调用编排、任务调度、运行记录、评测、文件管理、日志聚合
- 第三层 云端执行层：容器实例创建、镜像管理、资源分配、Pod 生命周期、弹性伸缩、监控告警、自动部署
- 设计原则：业务逻辑与云上算力调度解耦，按需动态使用云资源，保证稳定性与高可用

### 3.2 详细业务实现架构（六层）

- 第一层 用户接入层：Web 浏览器、移动端网页、管理后台

- 第三层 网关与鉴权层：API Gateway、JWT 鉴权、限流、审计、统一异常处理
- 第四层 业务服务层：用户 / 项目 / 文件 / AI 编排 / 任务调度 / 评测 / 日志 / 管理服务
- 第五层 数据与缓存层：MySQL、MongoDB、Redis、RabbitMQ
- 第六层 云端执行层：Docker、Kubernetes、Helm、KubeSphere、Metrics Server、Prometheus、Grafana、Loki

## 4. 痛难点与解决方案

### 4.1 前端部分

- Q1：xterm.js 还要不要保留？
  - 主界面改用 Monaco Editor + 日志展示 + WebSocket 状态流为主
  - xterm.js 降级为「高级模式 / 容器终端入口」用于 shell 调试
  - 原因：项目核心是开发实验室而非命令行练习；编辑器更符合评委认知；日志 / 报错 / AI 联动效果更好
- Q2：如何实现实时运行反馈？
  - WebSocket 推送
    - 任务状态变化
    - 日志实时输出
    - 容器启动进度
    - 资源占用
    - AI 二次建议
  - 点击运行后页面不刷新，仅更新工作台状态
- Q3：如何实现多角色权限？
  - 登录后用户信息存入全局 store，按身份动态渲染
  - 普通用户：创建项目 / 运行代码 / 使用 AI
  - 教师 / 管理员：发布实验模板 / 查看运行记录 / 回收资源
  - 超级管理员：管理镜像 / 集群配额 / 用户权限 / 审计日志

### 4.2 后端部分

- Q1：如何同时支撑 AI 对话与代码运行？
  - 微服务化拆分（避免互相阻塞）
    - 用户与权限服务
    - 项目与文件服务
    - AI 编排服务
    - 任务调度服务
    - 容器运行服务
    - 日志与监控服务
    - 评测服务
    - 管理后台服务
- Q2：如何管理多类型数据？
  - MySQL：用户 / 角色 / 项目元数据 / 实验模板 / 资源配额
  - MongoDB：对话上下文 / 代码版本快照 / 任务详情
  - Redis：任务队列 / WebSocket 会话 / 运行态缓存
  - 宿主机：源代码包 / 运行结果文件 / 上传数据集
- Q3：如何让 AI 真正参与开发流程？
  - 独立 AI 编排服务
    - prompt 模板管理
    - 多模型路由
    - 历史上下文压缩
    - 代码补全与解释
    - 报错分析
    - 根据运行结果二次修复建议
    - 自动生成测试样例
  - AI 作为开发辅助中枢，不直接接管业务

### 4.3 K8S 部分

- Q1：如何为每个用户快速分配隔离的开发环境？
  - 模板镜像 + Namespace / 标签隔离 + 动态创建 Pod / Job
    - 轻交互场景：短生命周期 Pod
    - 批处理场景：Job
    - 长时开发场景：Deployment + PVC
  - 实例附带：用户 ID / 项目 ID / 资源上限 / 运行时类型 / 生命周期标签
  - 实现多租户隔离与实例回收
- Q2：如何控制资源滥用？
  - K8S 层：ResourceQuota / LimitRange / HPA / Pod 优先级 / 节点亲和与污点 / TTL 自动回收
  - 后端层：配额队列（沿用「云平台算力队列 + Redis」思路）
- Q3：如何区分容器运行失败原因？
  - docker-client + k8s-client 多角度监测，构建三级诊断
    - 第一级：Pod 调度与拉取镜像异常
    - 第二级：容器启动失败或探针失败
    - 第三级：应用内部报错 / 超时 / 内存溢出 / 端口未监听
  - 前端展示「运行状态树」，AI 自动解释错误原因
- Q4：如何实现一键部署与滚动更新？
  - 云端继续使用 Helm + CI/CD（沿用 DevOps + Helm + KubeSphere + Metrics Server）
