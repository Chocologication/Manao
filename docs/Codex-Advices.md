# 码瑙项目 POC 可行性验证建议

## 背景约束

根据当前 PRD 与补充信息，本项目定位如下：

- 项目性质：个人/小组比赛项目，不要求生产级，但用户体验至少需要达到中等水平。
- 演示并发：真实并发用户小于 20 人。
- 技术优势：开发者更熟悉后端。
- 人员安排：时间和精力相对充裕，计划全栈完成。

因此，POC 不建议按完整功能模块顺序推进，而应按“项目成败风险”从高到低验证。核心目标是先证明：

```text
Monaco 编辑代码
-> 后端保存项目文件
-> 后端调用 Kubernetes 创建运行任务
-> 实时返回日志和状态
-> AI 基于运行结果给出分析建议
-> 自动清理运行资源
```

只要这条链路跑通，项目的核心成立。

## POC 风险优先级

| 优先级 | POC 主题 | 主要风险 | 最小验证内容 | 通过标准 |
| --- | --- | --- | --- | --- |
| 1 | K8S 动态运行代码闭环 | 这是项目核心卖点。如果不能从后端创建容器、运行代码、回收资源，平台会退化成普通 AI 编辑器 | 后端接口接收代码或项目路径，调用 Kubernetes Java Client 创建 Pod 或 Job，运行 Python/Java/Node 任一模板，返回状态、退出码、日志，并自动清理资源 | 至少稳定识别成功、编译/运行错误、超时三类结果；连续运行 20 个任务不打爆集群 |
| 2 | 实时日志与状态流 | 比赛演示时，用户体验主要依赖“点击运行后立即有反馈” | 前端点击运行，后端通过 WebSocket 或 SSE 推送排队中、拉镜像、运行中、完成/失败、日志行 | 页面不刷新即可看到日志流；失败原因能区分镜像拉取失败、容器启动失败、程序内部报错 |
| 3 | 项目文件到容器的挂载/注入方案 | 在线编辑代码到云端运行跨越文件系统、存储和容器边界，容易成为实现卡点 | 做一个最小项目：前端编辑文件，后端保存，运行时把文件注入容器。优先验证 ConfigMap、临时目录、PVC、打包上传中哪种最顺手 | 修改代码后再次运行能使用最新内容；不同用户和项目之间文件不串；任务结束后临时资源能清理 |
| 4 | AI 与运行结果联动 | AI 调用本身不难，难点是绑定当前项目、当前文件、运行日志和错误信息形成闭环 | 运行失败后，把代码片段、错误日志、退出码传给 AI 编排服务，返回原因分析和修改建议 | AI 建议能引用当前错误日志；默认不直接修改代码；前端能在右侧面板展示建议 |
| 5 | Monaco 工作台最小体验 | 开发者更熟后端，前端复杂度需要尽早暴露；中等用户体验至少要有可用工作台 | 实现左侧文件树、中间 Monaco 编辑器、右侧 AI 面板、底部日志面板、运行按钮 | 评委能在 30 秒内看懂打开项目、修改代码、运行、查看日志、询问 AI 的完整流程 |
| 6 | 配额、并发与资源回收 | 并发不高，但必须避免演示时容器堆积或节点资源耗尽 | Redis 或数据库记录用户运行中任务数；K8S 设置 CPU/内存 limit；任务 TTL 自动清理 | 单用户不能无限创建任务；20 个并发任务后系统仍能响应；异常任务能自动回收 |
| 7 | 用户、权限、团队最小闭环 | 权限不是最大技术风险，但会影响比赛演示故事完整性 | 先只做普通用户、团队所有者、管理员三类角色。团队任务只做创建、加入、分配模板、关闭任务 | 能演示个人项目和团队任务的区别；关闭团队任务后相关资源能被回收 |
| 8 | 监控展示与 KubeSphere/Grafana 接入 | 展示价值高，但不是核心链路前置条件 | 接入 Metrics Server 或 KubeSphere 页面，前端展示任务资源占用的简化数据 | 能看到 CPU、内存、运行任务数、失败任务数；满足比赛演示即可 |
| 9 | 多存储组合验证 | MySQL、MongoDB、Redis、对象存储全量引入会提高集成成本 | MySQL 存用户、项目、任务；Redis 存运行态；MongoDB 或 MinIO 先选一个验证日志或文件存储 | 数据能支撑核心闭环即可，不要一开始把所有存储铺满 |
| 10 | CI/CD、Helm、一键部署 | 对比赛加分，但不应压过核心功能 | 写一个最小 Helm Chart 或部署脚本，能部署前端、后端和必要中间件 | 换机器或重建环境时能复现演示系统 |

## 推荐执行阶段

### 第一阶段：核心闭环

优先验证以下链路：

```text
Monaco 编辑代码
-> 后端保存文件
-> 创建 K8S Job
-> 实时日志返回
-> AI 分析错误
-> 清理资源
```

这一阶段只需要支持一种到三种运行环境即可，建议从 Python 开始，再扩展 Java 或 Node.js。

### 第二阶段：比赛观感

在核心闭环稳定后，补齐演示体验：

- 开发工作台界面。
- 运行状态树。
- 日志面板。
- 资源监控卡片。
- 团队任务演示。
- 管理员模板配置。

这一阶段目标不是功能完整，而是让评委能直观看到“AI 云端开发实验室”的产品形态。

### 第三阶段：完整性补强

最后再补充完整平台能力：

- 权限细化。
- 模板版本管理。
- 审计日志。
- 对象存储。
- Grafana/KubeSphere 展示。
- Helm 或 CI/CD 部署脚本。

## 技术取舍建议

POC 阶段不建议优先做以下内容：

- 完整微服务拆分。
- 完整团队协作系统。
- 完整对象存储体系。
- 完整监控告警体系。
- 完整 CI/CD 流水线。

更适合当前比赛项目的路线是：

```text
后端保持模块化单体或少量服务
-> 先跑通 K8S 运行闭环
-> 再用前端工作台把核心能力展示出来
```

这样能最大限度发挥后端优势，同时避免被过重的基础设施和低价值边缘功能拖慢进度。
