## 1. 从闭环推导最小职责

目标是：用户下达任务 → Pi 理解需求 → 读改代码 → 构建测试 → 启动应用 → CRUD 验证 → 失败修复 → 用户验收。构建或接口验证失败后，Pi 可以多次返回修改环节。

这个目标需要三种能力：Pi 理解目标并决定下一步；项目工具执行真实操作；操作结果回到 Pi 和用户，作为修复与验收依据。用户验收是独立结果，不能由 Pi 的结束消息替代。

不为“理解需求”“制定计划”“修复”各做一个服务，也不把整条链路编排成固定工作流。Pi SDK 承担模型与工具循环；Manao 承担项目身份、写入条件、执行和 Run 的权威。固定的是完成条件与必要约束，读哪些文件、改什么代码、何时补测试以及怎样修复由 Pi 决定。

## 2. 四个可演示的阶段

| 阶段 | 原交付目标 | 原完成证据设计 | 当前状态（2026-10-19） |
| --- | --- | --- | --- |
| 1：Pi 真实读改测 | 最薄浏览器任务入口、服务器云模型配置、项目文件工具、开发命令执行；Pi 能直接修改专用 Spring Boot 项目并构建测试 | 给出一个小的接口修改目标，Pi 自行查代码、修改、运行真实 Maven 测试；提供一个可定位的编译或测试错误，Pi 根据执行结果修复并重新验证 | 已取得第一阶段PASS，后续修复验证边界见原记录 |
| 2：接上应用运行与反馈 | Pi 能停止旧 Run 并等待退出，以当前保存版本创建新 Run，读取状态和日志，请求项目应用接口 | 已有应用运行时接到任务，停止完成后才修改；新接口真实可访问；构建通过但应用启动或 HTTP 检查失败时，Pi 获取结果并修复后创建新 Run | 五任务代码及部署完成；验收未通过、暂停、NOT_GRANTED |
| 3：书籍 CRUD 与用户验收 | Pi 从目标完成书籍 REST 接口、项目 MySQL 持久化和自动验证；浏览器展示修改清单、验证结果及应用入口，用户可验收或提出修正 | 独立验收请求验证增查改删；项目 MySQL 实际存在对应记录；保留一条记录并停止、重跑应用后仍可查询；Pi 的会话结束与用户验收明确区分 | 用户基于实际使用确认使命提前完成；不把左侧原设计逐项记作独立实测PASS |
| 4：完成已约定的控制与恢复 | 暂停后交还编辑权、用户修改后继续、浏览器重进、服务异常后核对并手动继续，以及任务执行资源清理 | 暂停时命令及子进程确实结束，改动核对完毕后用户才能写入；浏览器断开不停止任务；服务异常后不盲目重放操作，核对后由用户继续；任务结束与用户删除项目不会留下开发执行资源 | 后续范围，本次未启动 |

阶段 1–3 是逐步扩展的一条真实链路，不分别建设完整文件平台、执行平台、任务平台。每阶段沿用同一套 task/project 标识与项目工具，避免先做演示代码再整体重写。

从阶段 1 的第一次真实写入开始，就加入项目身份校验、持久任务标识、项目写入占用、稳定操作标识、必要执行记录和命令上限；不能把这些放到阶段 4 才补。阶段 4 完善用户操作入口与异常核对，不承诺透明自动续跑。前三阶段证明核心编程价值，第四阶段完成已确认的首版体验；中间演示不记为完整首版验收。

阶段 1 的工具入口同时落实普通操作自动、其他高风险操作确认的已确认规则，专用验收项目数据库全部自动是明确授权例外。首版只做具体操作的确认／拒绝，批准绑定待执行操作及当前版本，不建设审批平台；文件与命令入口必须执行规则，不能只依赖提示词。自动执行的命令范围与需要确认的具体操作在阶段 1 接口设计中明确，不承诺通过通用分类器识别任意 Shell 的全部副作用。

首个阶段是 Pi 适配的验证点。如果读改测与真实反馈都需要另写大量通用编排来替 Pi 决定步骤，应回到候选比较，而不是继续扩大自研范围。

## 3. 最小新增实现与复用

建议保留现有前端和 Spring Boot 后端，新增一个 Node.js Pi 接入进程。后端增加项目限定工具和最小任务控制，不拆成新的任务、审批、执行微服务。

| 位置 | 负责什么 | 复用与新增 |
| --- | --- | --- |
| 浏览器工作台 | 输入目标、展示 Pi 消息及工具结果、显示差异、暂停／继续、用户验收 | 复用编辑器、文件树、Run 与日志展示；新增一个小任务面板，先轮询持久任务进度，后续有需要再优化传输 |
| Pi 接入进程 | 创建 Pi 会话、注入服务器模型配置、注册项目工具、接收任务、返回消息和工具事件 | 复用稳定 coding SDK 的工具循环、会话与上下文处理；显式控制资源加载，不执行用户项目的扩展代码 |
| 现有 Manao 后端 | 用户与项目鉴权、写入占用、操作核对、Run 控制、任务结果 | 复用文件 revision/digest/receipt、Run 的启动／停止观察、日志、项目依赖与清理；新增 AgentTask 与工具执行记录，给任务内操作补稳定标识 |
| 项目开发执行环境 | 在当前项目内执行 Shell、Maven 构建和测试，返回真实结果 | 复用 Java runner 与项目 Maven 缓存；新增临时执行入口、命令结果与停止核对，不新增工具链平台 |

首版的执行资源建议延用评估第 10.1 节的独立开发执行 Job，以命令为单位串行执行，复用已有 Job 的创建、观察和退出核对思路。它与应用 Run 分开。每命令调度存在开销；若真实修复任务证明这成为主要瓶颈，再将执行入口的内部实现换成一任务一个临时 Pod，保持项目工具接口不变。首版不建设执行池或常驻 Shell 服务。

Pi 的模型密钥与会话在控制进程中，用户代码在项目执行环境中。项目工具得到当前项目的能力，模型不直接获得平台数据库或集群管理权限。

## 4. 工具面保持小

| 工具组 | 用途与约束 |
| --- | --- |
| 文件 | 列目录、搜索、读取、编辑和创建文件；使用现有保存版本与操作回执，直接改当前项目 |
| 开发命令 | 在项目内执行 Shell、构建、测试；串行、有超时及输出上限，记录命令身份、退出结果和文件变更，Shell 改动核对后更新项目版本 |
| 应用运行 | stop、start、status、logs；停止结果确认后才改源码，启动绑定最新保存版本，每次重新运行创建新 Run |
| 应用请求 | 对当前项目应用发 HTTP 请求，返回状态与响应内容；目标由后端依据项目及 Run 确定，不暴露任意平台地址访问能力 |

Java 依赖先通过修改 `pom.xml` 和执行 Maven 正常处理，无需新增通用依赖管理框架。专用验收项目数据库已经授权全部自动；应用按项目配置使用 MySQL，首版无需先建设通用 SQL 工具、旧数据审批或任务受限账号。

文件写入和开发命令结果不明确时先核对，不因 Pi 再次请求或服务重启盲目重放。命令执行记录覆盖 Shell 对源码的改动，不能只给 edit/write 加版本保护。应用验证阶段与会改源码或共享 Maven 缓存的开发命令保持互斥；只请求应用 HTTP 接口可以在对应 Run 运行时进行。

最小持久内容为任务目标与状态、用户／项目／会话关联、当前执行身份与结果、保存版本、相关 Run 和验收结果。使用现有数据库和服务器会话存储，不额外引入消息队列、事件总线或独立编排数据库。服务异常后通过这些事实核对，等待用户手动继续。

## 5. 业务验收建议

2026-10-19 用户已依据实际书籍CRUD使用结果确认第三阶段使命提前完成，权威结论见[用户确认记录](../../poc4/docs/evidence/ai-stage3/acceptance.md)。以下保留最初的任务与独立验收建议作为设计历史，不是本轮逐项实测清单；不再默认另开第三阶段实现任务，也不据此改记第二阶段PASS。

首个自然语言任务可以固定为：

> 在当前 Spring Boot 项目中实现书籍 REST CRUD。书籍包含 id、title、author，使用当前项目 MySQL 持久化。完成构建测试，启动应用并验证增查改删，遇到错误自行修复。最后提供修改清单、测试结果和可访问接口，供我验收。

独立验收建议检查五个接口：`POST /books`、`GET /books`、`GET /books/{id}`、`PUT /books/{id}`、`DELETE /books/{id}`，覆盖修改值读回、删除后查询不存在，并检查数据库实际记录。保留另一条记录，在停止和新建 Run 后查询仍存在，以证明数据持久化。接口契约是待审阅的验收建议，不强制 Pi 采用某个 ORM、类结构或依赖组合。

验收脚本与预期结果可以固定，生成代码与修复过程不能预写成平台模板。失败修复需要一项确定可重现的故障，例如编译错误、字段映射错误或返回值错误；记录错误证据、Pi 的修复及重新验证结果，不能仅从“Pi 说已修复”推断通过。

用户看到文件改动、构建测试输出、相关 Run、HTTP 检查、持久化结果和应用入口后，明确验收或提出修正。收到修正后继续同一任务的上下文，但重新读取当前项目。用户验收前记为待验收，不记为自动验收通过。

## 6. 首版之外的工作与下一步

多 Agent、Python 与 Go/TS 用户项目适配、MCP/Skills 平台化、向量检索、通用工作流引擎、自动故障续跑、任意项目旧数据保护、执行池和复杂任务看板均不进入这条首轮实现链路。MCP/Skills 的后续接入复用同一项目工具约束，不需要现在建设插件平台。

第一阶段交付保留 receipt 直接写真实代码与固定 compile/test/package 的只读-copy构建。第二阶段五项实现补齐应用运行反馈，新增 application 与 app_http_get 两工具，日志有界tail、HTTP限GET；具体Interface与验证由第二阶段设计/计划及验收记录拥有。2026-10-16仅规划的表述属于历史快照；当前实现已发布、验收仍暂停，第三阶段使命已由用户于2026-10-19确认提前完成。后续安排应分别处理第二阶段未决证据和第四阶段范围，不能从本次文档更新自动开始实施。
